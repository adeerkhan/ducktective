**This is a neat, well-engineered protocol wrapper around a non-problem, or at least a problem that is almost never the bottleneck.**

### Harsh reality check

You are building a **discipline enforcer for LLM coding agents** that forces:

1. Reproduce first (exit-code gate).
2. Write a hypothesis + executable falsifying check.
3. Store a structured case file with arithmetic-verified verdicts.
4. Never let the model grade its own work.

The code quality, boundary enforcement, schema hardness, pure-string path handling, tree-kill, bounded capture, policyViolations(), blockers(), single-source SKILL.md, static site that can ingest a real cases.jsonl, installer that refuses edited files, and the deliberate refusal to build a graph/embeddings/multi-agent circus are all **excellent engineering**. The “verdict is unrepresentable unless predicted + exit_code agree” is genuinely better than 95% of the “debug skill / agent” noise on GitHub right now.

**None of that matters yet.**

As of the dated snapshot in the architecture itself (2026-09-15):

- Zero real reproduced cases that found a true root cause.
- M2–M9 empty by construction.
- The only rows are stops.
- No host agent has ever actually loaded the installed skill on a real box.
- Claude plugin path unexercised.
- Memory pairs never run.
- The kill criterion you yourselves wrote (“if nobody opens the case files, the differentiator is theoretical”) has already been met: nobody has opened them because there is nothing to open.

You have built a **beautiful empty ledger**. The instrument works. It has never measured the thing it was built to measure. That is the entire state of the project in one sentence, and it is damning.

### What are you actually developing?

A thin, installable **Skill** (not an agent, not a runtime, not a model) that turns “agent under pressure hallucinates a root cause” into “agent is forced to run a real command and an oracle before it is allowed to claim anything.”

It is the opposite of the usual over-engineered LLM debugging theatre (graphs, suspicion scoring, multi-agent detectives, knowledge graphs, cold scans, metamorphic oracles). You correctly parked all of that. Good.

But the product thesis is still weak:

- Most real bugs that coding agents hit today are either (a) trivial and the agent already finds them, or (b) environment/setup/dependency/config hell where “reproduce” itself is the hard part and your tools do not help.
- The cases where agents confidently invent wrong root causes **do** exist, but the cost of running this protocol (extra LLM turns + real test execution + writing checks) is high enough that most users will just tell the agent “fix it” and accept the occasional wrong patch.
- Persistent memory and the case file are the only durable differentiators, and you have zero evidence either is useful.

You are developing a **high-quality enforcement layer for a workflow almost nobody will adopt** until you prove the workflow actually saves time or prevents bad patches on real bugs.

### Direction: mostly right engineering, wrong prioritization

**Good / very good**

- Ruthless scope control. No custom graph, no embeddings, no daemon, no multi-agent cosplay.
- Every important rule is a type error / policy refusal at the store boundary, not prose.
- Real subprocess handling (tree kill, scrubbed NODE_TEST_*, atomic writes, head+tail capture).
- Schema + policy as the product.
- Static site that can render a real cases.jsonl without uploading anything.
- Guards that actually fail the build when docs rot or tools go undocumented.
- Honest measurement design (M1–M9, provenance, no invented zeros).

**Very bad**

- You shipped the entire spine, packaging, site, installer, and measurement framework **before** collecting even one real positive signal.
- The open item is “10–15 real bugs in repos you own.” That should have been item #1 in week 0, not the thing left after everything else is green.
- You are still writing architecture docs, site pages, and protocol explanations while the runlog is empty. That is classic “building the dashboard before the product has users” failure mode.
- The Claude plugin and Codex discovery paths are untested on real hosts. Distribution is still theoretical.
- Token/wall-clock and “was the claim right” metrics are hand-transcribed human judgement. The headline number is the least mechanical one. That is a red flag for self-deception.

You are going in the **right technical direction** (enforce, don’t suggest; store arithmetic, not prose; stay a skill, not an agent) but the **project direction is currently “polish the empty instrument.”** That is the wrong next move.

### What should happen next (ordered by actual value)

1. Stop all feature/docs/site work. Immediately.
2. Take 10–15 real bugs from repos you actually own or maintain. Run the skill (or force yourself to follow the protocol manually if the host agent still won’t load it). Log every investigation in the runlog with provenance=real. Do the blind baseline first for M9.
3. Measure whether anyone (including you) actually opened a case file and whether it changed a decision. If the answer is “no” after 15 bugs, the project is dead and you should kill it cleanly.
4. Only after you have real rows and at least a couple of “this actually helped” signals do you touch the parked items or improve the site.

Until the runlog has real data, every other line of code or documentation is pure self-deception.

### Updated design.md

Below is a ruthlessly pruned, current-state design document that replaces the aspirational one. It is constrained to what is actually built, what the architecture already admits is empty, and what the only remaining decision is.

```markdown
# Ducktective — Design (updated 2026-09-15)

**Status.** The instrument is built and green. The product is unproven.  
All numbers live only in `node evals/runlog.mjs --report`. This document never restates them.

## 1. What it is

A thin, installable Skill (not an agent, not a runtime, not a model) that sits above any host coding agent and enforces three hard rules:

1. Reproduce before any localisation or reasoning is allowed.
2. Every hypothesis must be accompanied by an executable falsifying check that is actually run.
3. The only thing that may be stored is a structured case file whose verdicts are arithmetic consequences of predicted outcome + exit code.

It never edits code. It never grades itself. The host model still decides the hypothesis and the check; the tools own every verdict and every store write.

Explicit non-goals (unchanged and still correct):

- No custom call graph, no suspicion scoring, no multi-agent roles, no knowledge-graph server, no embeddings, no background scanning, no oracle-free/metamorphic mode, no leaderboard claims.

## 2. Why it exists

Coding agents produce confident, plausible, wrong root causes.  
The usual response is more scaffolding (graphs, memory, multi-agent theatre).  
Ducktective’s bet is the opposite: make the bad behaviour unrepresentable by turning the critical steps into type errors at process boundaries.

## 3. Current spine (what actually ships)
```

user asks host agent to investigate
│
▼
reproduce.mjs ──exit 1──▶ does_not_reproduce (zero candidates) → write_case → STOP
│ exit 0
▼
seed ≤5 candidates (traceback + fail-only coverage order)
│
▼
run_check.mjs (hypothesis + predicted + check + optional control)
│ confirmed / falsified / inconclusive
▼
write_case.mjs (schema + policyViolations — only arithmetic-consistent verdicts accepted)
│
▼
.ducktective/cases.jsonl + cases/<id>.md

```

Exit-code contract, policy rules 1–8, evidence rule (“reproduced” requires in-repo evidence), id containment, tree-kill, bounded capture, and pure-string path classification are all implemented and tested. See architecture.md §§4–8 for the exact mechanisms.

## 4. What is deliberately not built

Everything in the “parked” table of architecture.md §13 remains parked.
Triggers are evidence-shaped. None have fired. Do not un-park any of them until the runlog has real positive signal.

## 5. Measurement — the only thing that matters now

The project has one kill criterion:

> If, after 10–15 real bugs, nobody (including the author) opens the case files or the files never change a decision, the differentiator is theoretical and the project should be archived.

M1–M9 exist. The ledger is honest (provenance, no invented zeros, human judgement labelled as such).
Current state: the only real rows are stops. Every interesting metric is empty by construction.

**Required next actions (in order):**

1. Collect 10–15 real bugs from repositories the author actually owns or maintains.
2. For each bug, run a bare baseline **before** the skill touches it (M9). Log `not-run` rather than a contaminated score.
3. Run the full protocol (or force the host agent to follow it). Log every investigation with `provenance=real`.
4. For at least three bugs, run the memory pair protocol (blind with store moved aside, then restored).
5. After the sample, read `node evals/runlog.mjs --report`. Decide, on a fixed date, whether the case files were opened and whether any decision changed.
6. Only then consider further work.

No feature, documentation, site, or packaging work outranks the above.

## 6. Distribution

- One-command installer for Claude Code, Codex, and generic agents skills directories. Verified for file placement, idempotency, and edited-file refusal.
- Claude Code plugin manifests exist and are pinned by tests. Never exercised on a real Claude box.
- Skill-only by design. No daemon, no MCP server.

Until a real host agent has loaded the skill and produced a non-stop case, distribution claims remain theoretical.

## 7. Known hard limits (still true)

- `--verify` is same-machine/same-tree only.
- Token and wall-clock numbers are host-reported and hand-transcribed.
- Whether the accused line was the true cause is human judgement after the fix.
- Frame parsing for jest/vitest/go/rspec is unproven.
- Site demo engine has no tests; ranking path checked by eye only.
- Site localStorage store and product JSONL store are deliberately separate.

## 8. Decision rule

The next commit that is allowed is one that adds a real row to the runlog.
Everything else is noise until the ledger is no longer empty.

If the sample produces no evidence that case files are opened or change decisions, archive the repository. Do not pivot into graphs, cold scans, or metamorphic oracles. The thesis was enforcement + memory; if that thesis fails on real bugs, the project is finished.
```

That is the updated design. It is shorter, colder, and forces the only decision that actually matters. Everything else is polish on an empty instrument.
